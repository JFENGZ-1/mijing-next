# 微信小程序遗留项目对抗式审计报告

审计日期：2026-07-11  
审计范围：`会员端/`、`管理端/`、`tools/audit-mini-programs.ps1`、`docs/generated/` 全部产物  
原则：本报告只复核和归纳，不修改两个小程序的业务源码。

## 1. 结论摘要

当前代码是两个已经编译成微信小程序产物的 uni-app/Vue 2 应用，不是可正常维护的源工程。前端文件基本齐全，185 个注册页面都具备 `.js/.json/.wxml/.wxss` 四件套，JSON 可解析，组件文件在静态层面均可找到；但后端、原始 Vue 源码、构建配置、接口文档、数据库、对象存储配置、合法域名配置和会员端 AppID 均不完整，不能据此直接重新上线。

审计脚本对文件、页面、组件和 API 端点的基础盘点有价值。独立核验 `common/vendor.js` 中所有 `/b`、`/c`、`/common`、`/wx` 字面量后，会员端 49 个、管理端 264 个唯一端点均进入目录，API 端点字面量覆盖完整。生成物共记录 317 条导出（部分导出映射到相同端点）、502 个可识别调用点。

不过，生成的 47 条问题不能视为 47 个真实缺陷：事件识别至少有明确误报，资源识别存在系统性“把未知路径当后端资源”的偏差，导航只覆盖特定根目录和字面量，参数与响应数据结构也没有被真正提取。因此，生成物适合做索引，不适合直接作为验收结论。

## 2. 覆盖率与产物质量

### 2.1 文件与编码

- `file-inventory.csv` 记录 1765 个文件，与 PowerShell 的递归隐藏文件枚举一致；普通 `rg --files` 显示 1747 个，差额主要是 `.DS_Store` 等隐藏元数据，并非漏扫。
- 会员端 386 个文件、管理端 1379 个文件；文本读取错误和 JSON 解析错误均为 0。
- 生成 CSV/JSON 是无 BOM UTF-8。现代工具读取正常，中文无乱码；老版 Excel 直接双击 CSV 可能按本地 ANSI 猜测而乱码，属于消费端兼容风险，不是内容损坏。
- 脚本仅把 `.js/.json/.wxml/.wxss/.wxs` 当文本。对当前产物足够，但以后若加入 `.map/.md/.txt/.html` 不会做内容审计。
- `Get-Content` 未显式指定编码，依赖 PowerShell 7 的 UTF-8 默认行为；在 Windows PowerShell 5.1 复跑可能出现编码差异。建议固定 `-Encoding utf8` 并在脚本开头校验 `$PSVersionTable.PSVersion`。

### 2.2 页面与分包

- `page-inventory.csv` 共 185 个注册页面：会员端 35、管理端 150，四件套均完整。
- 分包大小按目录物理字节计算，适合容量预警，但不等于微信上传后的真实包大小；它没有模拟微信编译器压缩、忽略规则和依赖裁剪。
- 脚本只验证“注册页面是否有文件”，未反查“存在但未注册的页面四件套”。遗留页面、废弃页面和可恢复但未注册页面仍可能漏出。

### 2.3 组件

- 共识别 1942 个 `usingComponents` 引用，静态路径均存在。
- `Exists` 只要求 `.js`、`.json` 或裸文件任一存在，门槛过低；一个只有 JSON、缺 WXML/WXSS/JS 的损坏组件也会被判定存在。正确规则应按组件类型核验完整文件集，并验证组件 JSON 的 `component: true`。
- 外部协议引用被直接视作存在；当前未发现插件组件证据，但该逻辑未来会掩盖插件缺失。

### 2.4 API

- 端点字面量覆盖经独立比对为 100%：会员端 49/49，管理端 264/264。
- 目录中的 Method 全部是 POST，与编译包中的统一请求封装一致；Content-Type 和 `isQuery/isWrite/useSlave` 元数据也被提取。
- `api-catalog.csv` 有 317 条而唯一端点为 313 条，原因是不同导出名可复用同一路径，不应把导出数当接口数。
- `api-usages.csv` 只匹配编译器生成的 `(0,module.export)(...)` 形式。别名调用、间接调用、存入变量后调用、store action 内调用以及动态分发均可能漏报。
- `ArgumentPreview` 是调用后 260 字符的文本片段，不是参数 AST，不保证止于本次调用，也不能作为请求 schema。
- API 正则要求 `custom:{...}`，若存在没有 custom 元数据的请求会漏掉。此次字面量端点比对未发现漏掉的已知业务端点，但不能证明动态 URL 不存在。

### 2.5 导航

- 生成物识别 299 条导航引用，其中管理端 12 条未注册。
- 这 12 条集中指向 `/pageReport/coach/privateDetail` 和 `/pageReport/coach/leagueDelete`，实际文件和 app.json 注册项均不存在，且被多个报表页面引用。它们是高置信度的遗失页面/遗留死链，不是单点拼写误差。
- 导航正则只接受预设的页面根目录、字面量 `url/path`，不识别拼接后才形成的路由、变量路由、WXML `navigator` 的所有变体和自定义 `href` 封装的完整语义。管理端还重写了全局导航函数，因此仅凭 CSV 无法证明无其他死链。
- 对 `navigateToMiniProgram` 的判定依赖前后 620 字符上下文，压缩代码中可能误关联邻近调用。

### 2.6 事件

- 共识别 1944 个编译 WXML 事件绑定，报告 35 个缺失 handler（会员端 2、管理端 33）。
- 至少 3 个是明确误报：`pageReport/component/popupTop` 的 `close`、`pageReport/teacherMembership/personalSalaryDetail` 的 `remark`、`pages/home/home` 的 `confirm` 在同名 JS 中存在，但脚本的 handler 定义正则没有覆盖编译后的函数声明/对象结构。
- 其余项中，不少是组件向父级 `$emit` 的事件名或跨组件代理，不能只在“同名 WXML 对应 JS”中查找。需结合 `usingComponents`、父子组件关系和运行时点击路径确认。
- 因此“35 个缺失事件处理器”是候选集合，不是上线阻断数量。建议脚本增加函数声明、`methods` 编译形态、mixin 和父子组件事件的识别，并把结果分为“确定缺失/跨组件待确认/已找到”。

### 2.7 资源

- 资源表共 1027 条引用。静态本地资源存在性检查本身有效。
- 最大的系统性误判在于：JS 中任何匹配到、但本地不存在的图片/视频路径都会被标为 `backend_uploadURL`，从而永远不会产生 `missing_asset`。这会把真实拼写错误、删失文件、错误相对路径一并隐藏。
- `imgsrc(...)` 确实证明大量业务图片需要后端返回的 `uploadURL` 前缀；但只有处于明确 `imgsrc` 调用、接口响应字段或已知后端资源字段中的值，才能判为后端资源。不能仅以“不存在”反推“来自后端”。
- 对协议相对 URL `//...` 一律标为运行时资源也过于宽松；微信合法域名与 HTTPS 要求仍需逐项验证。

## 3. 可恢复的后端接口契约

### 3.1 网络基础契约

- 会员端编译包硬编码环境：测试 `https://test.songguoyueke.com/api`，生产 `https://interface.songguoyueke.com/api`。
- 管理端同样通过 `baseUrl` 常量和统一请求实例访问后端；上线前必须从其 vendor 模块确认并替换为当前所有者可控制的域名。
- 所有已发现业务接口使用 POST。
- 请求体主要为 `application/json` 或 `application/x-www-form-urlencoded`。
- 会员端请求拦截器把 `deviceId`、`tokenId` 放入 URL query，并从 body 移除；登录接口 `/wxlogin` 不附 token。
- 管理端以独立 token store 工作，登录态和权限模型与会员端不同，不能共用简单 session。
- 查询请求可能加 `dsname: slave` 请求头；写入后两秒内查询避免走从库。这表明旧后端存在主从读写一致性约定。重建时要么保留该语义，要么让网关忽略该头并保证读己之写。
- 响应拦截器直接返回 `response.data`。页面普遍按业务 `code` 判断，成功码核心为 `200`；会员登录还处理 `560` 并携带 `siteInfo` 跳转无登录页。
- 网络错误只显示“网络不稳定”，没有统一业务错误规范。重建建议统一 `{code, message, data}`，同时为兼容旧前端在顶层保留现有字段。

### 3.2 接口域划分

会员端：

- `/c/user/*` 46 个：微信登录、用户资料、门店/教练、团课/私教排期、预约与取消、会员卡、余额/次数、订单、通知、赠卡/领卡、微信卡包。
- `/common/dict`：返回默认卡图、课程图、员工头像、商标、用户头像和 `uploadURL`。
- `/wx/getUnionId`、`/wx/getWeixinPhoneNumber`：微信 code 换 union/open 身份和手机号。

管理端：

- `/b/arrange/*` 28 个：排课、调课、停课、复制计划、课程计划详情和背景。
- `/b/card/*` 16 个：卡种、价格、适用课程、卡背景、卡规则。
- `/b/course/*` 15 个：团课/私教、教室、标签、教练、课程保存。
- `/b/linkage/*` 24 个：连锁门店、跨店卡/课程/人员关系。
- `/b/mainplan/*` 13 个：主排期、团课计划、预约和签到相关。
- `/b/manageuser/*` 53 个：会员、会员卡、余额/次数调整、标签、备注、订单、拼音索引。
- `/b/report2/*` 66 个：营业、课程、教练、会员、薪资、提醒、排行等报表。
- `/b/staff/*`、`/b/staffuser/*` 共 25 个：员工、角色、权限、登录、门店配置、上下班。
- `/b/platform/*`、`/b/setting/*`：平台配置、支付/业务设置和字典。
- `/b/export/*`：导出任务或导出数据。
- `/b/userorder/*`：订单与收款调整。
- `/common/const`、`/common/dict`：枚举、默认资源和上传域名。
- `/wx/*`：微信身份及手机号解密。

完整端点、导出名、Content-Type 和读写标志以 `docs/generated/api-catalog.csv` 为准。它是重建路由清单，但不是完整 OpenAPI；请求字段应从 `api-usages.csv` 回到调用页面逐项建模，响应字段应从 `.then(...)` 消费代码反推并通过契约测试锁定。

## 4. 核心数据实体

从接口命名、路由参数和页面状态可恢复出以下最小领域模型：

- Tenant/Site：品牌或租户、门店、连锁关系、营业时间、门店配置、图片域名。
- Staff/Role/Permission：员工、教练、销售、角色、权限、在职状态、邀请关系、工作状态。
- WeChatIdentity：appId 维度的 openid/unionId、登录 code、手机号授权、tokenId/deviceId。
- User/Member：用户资料、头像、手机号、生日、性别、标签、备注、黑名单/屏蔽状态。
- Course/Room/Tag：团课、私教课、教室、课程标签、时长、价格、扣课规则、授课教练。
- Plan/Arrange/Appointment：排课计划、周期、场次、容量、预约、取消、候补、签到、旷课、停课/调课。
- Card/CardProduct/UserCard：卡种、卡面、适用门店/课程、有效期、次数或余额、会员持卡实例、转卡/赠卡。
- Order/Payment/AmountLog：订单、订单明细、应收实收、支付方式、退款/撤销、余额与次数变更日志。
- Report/Snapshot：营业日报、课程报表、教练业绩、会员增长、薪资、到期/生日/缺课等提醒。
- Notice/Share/Invite：公告、分享参数、员工邀请、会员领卡链接。
- MediaAsset/Dictionary：上传文件、默认图片、富文本/视频、枚举常量。

所有实体必须带租户/门店边界和审计字段。旧接口大量使用 `siteId/userId/cardId/courseId/orderId/staffId`，同时存在大小写和下划线混用（如 `userId/user_id`、`courseId/courseid`），兼容层需要接受旧字段，内部模型应统一命名。

## 5. 第三方与平台依赖

- 微信小程序登录、UnionID/OpenID、手机号授权；需要两端各自可控的 AppID/AppSecret 和主体资质。
- 管理端 `project.config.json` 有 AppID `wx144915b575a7792d`；会员端配置没有 AppID，是直接阻断项。
- 微信卡包接口（会员端存在卡包参数组装）；需确认原商户/卡券能力是否仍可用。
- 微信支付能力很可能由订单/选卡支付流程驱动，但静态检索未能确认完整 `requestPayment` 调用链；必须按真机流程验证，不能假设无需支付商户号。
- 对象存储/CDN：`/common/dict` 返回 `uploadURL`，头像和资料页存在上传逻辑。需恢复上传接口、文件权限、HTTPS/CDN 域名和历史资源。
- uView UI、uni-app Vue 2 运行时、Vuex、Lodash、Babel runtime、图片裁剪器、富文本解析器、图表/Canvas 等均以编译产物内嵌；缺少原始依赖清单和许可证清单。
- 管理端存在跳转其他小程序；目标 AppID、path、开放关系和权限需从对应页面代码及微信后台核实。
- 隐私组件已存在，但 app.json 的隐私权限声明非常薄弱；手机号、相册/上传等能力需要按当前微信审核规则重新配置隐私协议和接口声明。

## 6. 上线阻断项（按优先级）

### P0：未解决不可上线

1. 后端和数据库遗失：313 个唯一业务路由、鉴权、权限、报表、订单和排课事务均需重建。
2. 账号资产不完整：会员端 AppID 缺失；两端 AppSecret、微信主体、管理员权限、支付商户号、卡包能力未知。
3. 域名与基础设施归属未知：旧生产域名、TLS、微信 request/upload/download 合法域名、对象存储和历史图片必须迁移到可控账户。
4. 认证契约未复原：会员端 tokenId/deviceId、管理端 token、UnionID/OpenID、手机号解密和 560 分支必须端到端跑通。
5. 数据不可用：会员、卡、余额、次数、订单、排课属于强一致业务；没有原库或可验证迁移数据，不能面向真实用户开放。
6. 两个明确遗失路由 `/pageReport/coach/privateDetail`、`/pageReport/coach/leagueDelete` 被多处引用，需恢复页面或删除入口。

### P1：提审或生产运行高风险

1. 仅有编译产物，无 `.vue` 源码、`package.json`、manifest、构建脚本和 source map；可做应急修补，但不可持续维护。
2. 请求/响应 schema、错误码、分页、金额单位、时区、幂等和并发规则未文档化；特别是排课、扣次、余额、支付、退款必须先建契约测试。
3. 35 个事件候选需人工逐页验证，不能把审计脚本结果直接关闭或直接判故障。
4. 图片资源审计存在系统性漏报，必须修正判定后重新检查。
5. 隐私协议、手机号授权、相册上传、第三方小程序跳转、用户数据删除机制需按当前微信规则复审。
6. 管理端包体物理总量约 7.6 MB，虽有分包，但需用微信开发者工具真实构建验证主包/分包上限、重复依赖和上传结果。

### P2：恢复后应补齐

1. 清理 `.DS_Store`、恢复源码仓库和可重复构建环境。
2. 生成 OpenAPI、数据库迁移、权限矩阵、状态机、错误码表、数据字典和灾备方案。
3. 增加登录、排课、预约、扣次、售卡、支付、退款、跨店、报表的端到端回归。
4. 梳理内嵌第三方库版本、许可证和已知安全漏洞。

## 7. 对审计脚本的改进建议

本轮未修改脚本，因为当前产物的 API 端点主体是可靠的，而事件/资源问题需要先定义更严格语义，贸然改正则会制造另一批误报。下一版建议：

1. 显式固定 UTF-8 读取和 PowerShell 版本。
2. 增加未注册页面四件套、组件四件套及 `component: true` 校验。
3. 用 JS parser 或最少以括号平衡解析 API 调用参数，替代 260 字符预览。
4. 导航同时扫描 `navigator`、封装 `href`、拼接路由和 app.json tabBar，并区分“确定路由”和“动态候选”。
5. 事件识别覆盖函数声明、编译 methods、mixin、父子组件 `$emit`，输出证据等级。
6. 资源只在明确 `imgsrc`/后端响应字段时标为 backend；未知不存在路径应标 `unresolved` 并产生告警。
7. 为生成物添加脚本版本、生成时间、源文件总哈希和规则版本，使复跑可追溯。

## 8. 建议的恢复顺序

先冻结这份编译产物并做哈希基线；随后取得微信主体、AppID/AppSecret、域名、对象存储和可能的数据库备份；以 `api-catalog.csv` 建兼容网关和 OpenAPI 骨架；按登录与字典、门店员工权限、会员卡、课程排课、预约扣次、订单支付、报表的顺序恢复领域；每完成一个领域，用现有小程序做黑盒契约测试。只有两端核心旅程在微信开发者工具和真机通过、数据核对与回滚方案完成后，才进入提审。
