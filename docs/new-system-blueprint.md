# 新觅境约课系统第一性原理蓝图

> 定位：从零建设新的前后端系统。旧会员端与旧管理端仅作为业务范围、交互和异常场景参考，不复用旧编译代码、旧接口、旧数据库结构、旧令牌协议或旧安全设计。

## 1. 已确定技术基线

### 1.1 前端

- uni-app
- Vue 3
- TypeScript
- Vite
- Pinia
- uView Plus，替代停止维护的 uView UI
- SCSS 设计变量
- 会员端与管理端分别构建为微信小程序
- 共享领域类型、API SDK、鉴权、日期金额处理与基础业务组件

uView Plus只解决基础控件替代，不承担领域规则。会员卡、课程场次、排课日历、权益流水、预约状态、权限选择器等必须建设自有业务组件，避免再次被 UI 库的数据结构绑定。

### 1.2 后端

- PHP 8.2 或更高的受支持版本
- 推荐 Laravel；若团队已有成熟 PHP 框架，可在满足本文约束时替换
- MySQL 8.x，统一 `utf8mb4`；当前本地基线为 8.3.0
- Redis：会话、幂等键、分布式锁、频率限制、短时缓存和队列
- 对象存储：头像、课程图片、协议附件、导出文件和审核证据
- Nginx + PHP-FPM
- OpenAPI 3 接口文档
- 数据库迁移、种子数据、队列任务、定时任务和审计日志
- Docker Compose 提供一致的本地与测试环境

### 1.3 MySQL 8.0 的主动约束

MySQL 8.0 提供窗口函数、CTE、可执行的检查约束和更好的 JSON 能力，但核心业务仍按可移植、显式事务原则设计：

- 复杂报表可以使用窗口函数和 CTE，但高频跨期报表仍使用明确的汇总表或离线计算任务。
- 重要业务约束同时在应用层、唯一索引和必要的 `CHECK` 中表达，不能只依赖其中一层。
- JSON 字段只保存扩展快照或第三方原始报文，不作为核心可查询关系模型。
- 金额使用 `DECIMAL(18,2)` 或以分为单位的 `BIGINT`，项目内只能选择一种主规范。
- 时间统一存储为 UTC `DATETIME`，应用层转换为场馆时区；若业务只在中国运营，也必须显式固定 `Asia/Shanghai`，禁止依赖服务器默认时区。
- 所有表使用 InnoDB、明确主键、必要索引与外键策略；高频大表按查询模式设计联合索引。
- 不使用数据库触发器隐藏业务变化，权益、资金和审计均由应用服务显式写入。

## 2. 系统存在的根本理由

系统必须持续回答五个问题：

1. 谁在代表哪个身份和场馆操作？
2. 什么课程在何时、何地、由谁提供，容量是多少？
3. 会员拥有什么权益，权益为什么增加或减少？
4. 一次预约从申请到履约经历了什么状态？
5. 每一笔钱如何从订单进入支付、退款和财务流水？

页面、接口、报表和通知全部是这五类事实的投影。任何无法追溯到事实和流水的功能都不能成为账务或权益真相。

## 3. 产品与租户边界

系统按 SaaS 多租户设计，但首版可以只运营一个品牌。

```text
平台
└── 租户/品牌 Tenant
    ├── 场馆 Site
    │   ├── 教室 Room
    │   ├── 员工 Staff
    │   ├── 课程与排课
    │   └── 会员与权益
    └── 连锁共享策略
```

每条业务数据必须带 `tenant_id`。与场馆相关的数据还必须带 `site_id` 或明确的适用场馆关系。前端传入的租户和场馆不能直接信任，后端从当前身份、角色和资源归属重新校验。

旧系统包含 `/b/linkage/*` 24 个接口，说明连锁门店、跨店课程、跨店卡和人员配置不是边缘功能。新系统首版应先保留数据模型和权限边界，但跨店消费可以在单店闭环稳定后开启。

## 4. 身份、账号与权限

### 4.1 身份模型

以下概念必须分离：

- `account`：系统登录主体。
- `wechat_identity`：按 AppID 保存 OpenID，必要时关联 UnionID。
- `member`：会员业务身份。
- `staff`：员工业务身份。
- `staff_site`：员工在某场馆的任职关系。
- `role` / `permission`：授权模型。
- `session`：短期登录会话，不等于业务身份。

同一个自然人可以同时是会员和员工，但两个身份的权限、数据和登录入口不能混淆。

### 4.2 登录

会员端：

1. `wx.login` 获取一次性 code。
2. 后端调用微信接口换取 OpenID/session key。
3. 查找或创建微信身份。
4. 绑定会员身份或进入注册流程。
5. 签发短期 access token 和可撤销 refresh token。

管理端：

1. 微信身份必须关联有效员工。
2. 员工必须在职且拥有至少一个场馆任职关系。
3. 登录后选择或恢复当前场馆。
4. 后端返回权限集合和数据范围。

严禁继承旧系统 `code=test`、URL 中 `tokenId`、客户端自报权限和永久令牌。令牌放在 `Authorization` 请求头；服务端支持撤销、过期、刷新、设备列表和异常登录审计。

### 4.3 权限

采用 RBAC + 数据范围：

- 平台管理员
- 租户所有者
- 场馆管理员
- 店长
- 教练
- 前台/会籍
- 财务
- 只读报表
- 自定义角色

权限粒度至少覆盖查看、创建、编辑、删除、审核、导出、金额调整、权益调整、退款、权限管理。敏感操作要求二次确认和独立审计。

对抗要求：员工不能修改自己的角色；不能授予自己没有的权限；不能通过改 `site_id` 越权；已离职员工的所有会话立即失效。

## 5. 组织、场馆和基础配置

旧系统包含品牌、门店切换、营业时间、门店状态、房间、员工、连锁配置和场馆展示配置。新系统需要：

- 租户/品牌
- 场馆资料、地址、电话、经纬度、Logo、门头图
- 场馆状态：筹备、营业、暂停营业、停用
- 营业时间和特殊休息日
- 教室/场地及容量
- 场馆级业务开关
- 场馆级会员协议和隐私文本版本
- 连锁共享策略

业务开关不能散落为自由字符串。建立带类型、默认值、作用域和变更审计的配置定义。旧 `clientConfig` 中已出现团课显示、私教显示、购卡入口、价格显示、排行榜、教练电话、过期课程、非会员/零余额/过期卡访问限制和公众号提示，应逐项转化为正式配置。

## 6. 会员域

### 6.1 会员档案

- 姓名、昵称、头像
- 手机号及验证状态
- 性别、生日
- 身高、体重等可选健康资料
- 身份证等高敏感字段默认不采集；确有业务必要时单独授权、加密和限制访问
- 标签、来源、跟进员工、备注
- 状态：潜客、正式会员、冻结、注销
- 创建来源、注册场馆、归属场馆

旧系统中的拼音搜索、标签、备注、访客提醒、生日提醒和会员分析说明会员 CRM 是真实需求。首版实现资料、搜索、标签和备注；自动营销在合规和通知能力稳定后实现。

### 6.2 数据隐私

- 最小化采集
- 字段级访问控制
- 高敏感字段加密
- 数据导出与注销流程
- 授权文本版本和同意记录
- 操作日志中脱敏
- 导出文件短时有效并记录下载人

## 7. 课程、教练与排课

### 7.1 课程定义

- 团课与私教为课程类型，不应复制两套完全独立模型
- 课程名称、图片、简介、时长、标签、难度
- 默认容量、适用教室、适用卡项
- 扣课规则、取消规则、候补规则
- 可见范围、可预约时间窗口
- 状态：草稿、启用、停用

### 7.2 教练

- 教练是员工能力标签，不应复制员工资料
- 可授课程、所属场馆、展示资料
- 工作时间、请假、停用
- 课酬规则独立于课程价格

### 7.3 排课

- `schedule_series`：周期排课规则
- `class_session`：实际单节课，是预约和履约的唯一目标
- 单节课保存课程、教练、教室、开始/结束时间、容量、预约窗口和规则快照
- 周期规则修改只能影响选定范围：仅本节、未来场次、整个系列
- 调课、停课、换教练、换教室均记录变更日志

旧管理端 `/b/arrange/*` 28 个和 `/b/mainplan/*` 13 个接口覆盖批量排课、复制、停课、撤销、调课、详情和签到，说明排课不是简单 CRUD。新系统必须先定义冲突检测：教练时间冲突、教室冲突、跨场馆通勤冲突、容量下降导致已有预约超额。

## 8. 会员卡与权益账本

### 8.1 卡产品

- 次卡
- 储值卡
- 时长/期限卡
- 组合权益卡

卡模板定义名称、售价、有效期、适用课程、适用场馆、扣减单位、使用限制、可转赠/冻结/续期规则。

### 8.2 持有卡

`member_card` 是会员持有实例，必须保存购买或发放时的规则快照，避免修改卡模板后改变历史权益。

状态建议：待生效、生效、冻结、过期、用尽、作废。

### 8.3 不可变权益流水

任何次数、余额、有效期变化都产生流水：

- 开卡/期初发放
- 购卡
- 充值
- 预约扣减
- 取消返还
- 场馆取消补偿
- 退款回收
- 转卡/赠卡
- 人工调整
- 过期

`member_card` 可以保存当前余额作为性能汇总，但真相来自流水。人工调整必须有原因、附件、操作者和审核人；不能提供直接编辑余额的接口。

对抗要求：重复请求不能重复扣减；余额不足不能变成负数；两次并发预约同一张卡必须串行或乐观锁失败；退款不能在权益已消费后无条件全额执行。

## 9. 预约、候补与履约状态机

### 9.1 预约状态

建议拆分“席位状态”和“履约状态”，避免旧系统用一个数字承载所有含义。

席位状态：

```text
PENDING → BOOKED → CANCELLED
       └→ WAITING → PROMOTED → BOOKED
```

履约状态：

```text
NOT_STARTED → CHECKED_IN → COMPLETED
                         └→ ABSENT
```

课程状态：计划中、开放预约、进行中、已完成、已取消。

### 9.2 核心不变量

- 可用席位不能小于零。
- 同一会员不能重复占用同一场次。
- 候补转正必须按明确顺序且原子占位。
- 取消是否返还权益由规则快照、取消方和时间共同决定。
- 场馆取消必须处理所有预约、候补、权益和通知。
- 签到、旷课、完成不能随意来回修改；纠错走补正流水。
- 预约与扣课要么同时成功，要么同时失败。

### 9.3 私教特有规则

私教预约还要处理教练可用时段、最小预约单位、跨日、请假、改约、锁定时段和一对多私教。不能只复刻旧页面上的上午/下午/晚上分组。

## 10. 商品、订单、支付和退款

### 10.1 订单

- 订单与支付分离
- 订单保存商品和价格快照
- 金额由后端计算，不能信任前端
- 订单号全局唯一
- 状态：待支付、支付中、已支付、已关闭、部分退款、已退款

### 10.2 微信支付

```text
创建订单
→ 创建预支付单
→ 小程序 requestPayment
→ 微信服务端回调验签
→ 幂等入账
→ 发放会员权益
```

前端成功回调不是支付真相。必须实现回调验签、金额和商户校验、重复通知幂等、主动查单、超时关单、补单、退款回调与日对账。

首版可以先不上在线支付，但数据库和应用服务不能把“人工发卡”伪装成微信支付订单。人工售卡、赠送和线上购买必须是不同来源。

## 11. 转赠、领卡、分享与二维码

旧会员端包含赠卡领卡、无登录课程分享、启动二维码 scene、会员二维码和微信卡包。

新系统处理：

- 课程分享：签名短链，只暴露公开课程数据；登录后才能预约。
- 赠卡/领卡：单独转赠单，包含发送方、接收方、卡、剩余权益快照、有效期、一次性令牌和审核状态。
- 分享令牌必须随机、短时、一次性、防重放，不能仅靠可枚举 ID。
- 小程序码由服务端调用微信 API 生成，scene 只放短标识，服务端解析真实参数。
- 会员签到二维码应使用短期动态码，不能使用永久会员 ID。
- 微信卡包属于可选集成，不进入 MVP；它不能替代系统权益账本。

## 12. 通知、提醒和协议

旧系统覆盖公告、课程提醒、取消、候补成功、生日、卡到期、余额不足、缺课、请假、访客等提醒。

新系统建立统一通知中心：

- 业务事件
- 通知模板
- 渠道：小程序订阅消息、站内消息，后续可扩展短信
- 发送任务
- 发送结果与失败原因
- 用户订阅与退订状态

通知不能嵌在事务中同步发送。业务事务提交后发布事件，由队列异步处理；失败可重试但必须幂等。

协议和隐私文本必须版本化，记录会员同意的具体版本、时间和来源。

## 13. 报表、排行、工资和导出

旧管理端 `/b/report2/*` 有 66 个端点，覆盖营业、课程、教练、会员、薪资、提醒和排行，是最大接口域。对抗结论是：不能按旧页面逐张报表直接写 SQL。

报表分层：

1. 事实表：订单、支付、退款、权益流水、预约、履约。
2. 业务查询：实时列表和当天汇总。
3. 日汇总表：按租户、场馆、日期、课程、教练和支付方式聚合。
4. 管理报表：从事实和汇总表生成。

任何报表数字必须可以下钻到底层事实。排行只是查询视图，不形成新的业务真相。

工资模块高风险，MVP暂缓。后续需支持固定课时、按人数、按课程金额、固定金额等旧系统已出现的规则，并保存规则版本和计算快照，禁止修改规则后重算已结算工资。

导出使用异步任务：生成文件、短时下载地址、权限校验、下载审计和自动过期。

## 14. 前端信息架构

### 14.1 会员端

主 Tab：

- 首页
- 约课
- 我的

核心页面：

- 启动和登录
- 选择场馆
- 场馆详情
- 通知
- 团课列表与详情
- 私教列表、教练详情和可约时间
- 预约确认、候补、取消
- 我的预约
- 我的会员卡和权益流水
- 会员资料
- 协议与隐私

后续页面：购卡支付、积分、排行、统计、赠卡领卡、微信卡包。

### 14.2 管理端

主 Tab 保留旧系统已经验证的工作模型：

- 今天：首页与当日任务
- 课程：课程、排课、签到
- 会员：搜索、档案、卡和流水
- 报表：核心经营指标
- 场馆：设置、员工、权限

管理端是高频工作工具，应紧凑、可扫描、少层级。避免营销式首页、巨型卡片和纯装饰元素。

### 14.3 uView Plus 替换策略

- 先定义设计变量，再配置 uView Plus 主题；不在页面散落颜色和间距。
- 建立适配层封装高频基础组件，降低未来 UI 库切换成本。
- 不直接复制旧 uView 组件路径、事件名和内部数据结构。
- 对表单统一错误展示、禁用、加载、重复提交保护。
- 对弹窗、日期、选择器、上传、空态和分页建立统一交互规范。
- 会员卡、排课日历、预约状态等领域组件由项目自己维护。

## 15. API 设计

新接口采用资源和业务动作相结合的 REST 风格，不复刻旧的全 POST 和控制器方法名。

示例：

```text
POST   /api/v1/auth/wechat/login
GET    /api/v1/sites
GET    /api/v1/class-sessions
POST   /api/v1/class-sessions/{id}/bookings
POST   /api/v1/bookings/{id}/cancel
POST   /api/v1/bookings/{id}/check-in
GET    /api/v1/members/{id}/cards
GET    /api/v1/member-cards/{id}/ledger
POST   /api/v1/orders
GET    /api/v1/orders/{id}
POST   /api/v1/refunds
```

统一响应包含业务数据和请求追踪 ID；错误使用稳定错误码、HTTP 状态和可展示消息。分页统一格式。创建与高风险写操作支持 `Idempotency-Key`。

OpenAPI 是前后端契约源，由它生成 TypeScript API 类型；禁止前后端手写两套不一致模型。

## 16. 数据库设计原则

所有核心表至少包含：

- `id`
- `tenant_id`
- 必要时 `site_id`
- `status`
- `version` 乐观锁
- `created_at`, `created_by`
- `updated_at`, `updated_by`

财务、权益和审计流水原则上不可物理删除。普通配置使用软删除时，唯一索引要考虑已删除记录冲突；MySQL 8.0仍没有 PostgreSQL 式部分索引，需通过业务唯一键、生成列或归档策略解决。

关键唯一约束示例：

- 微信身份：`appid + openid`
- 员工任职：`tenant_id + site_id + staff_id`
- 单场预约：`class_session_id + member_id + active_flag`
- 支付单：`merchant_id + out_trade_no`
- 幂等请求：`tenant_id + idempotency_key + operation`

## 17. 安全基线

- 关闭并禁止任何固定测试 code、万能密码和隐藏管理员。
- 认证和业务授权分离。
- 所有写接口进行租户、场馆、角色和资源归属校验。
- CSRF 对纯 Bearer API风险较低，但管理 Web 若使用 Cookie 必须防护。
- SQL 全部参数化。
- 上传校验 MIME、扩展名、大小、图片解码和访问权限。
- 限制登录、验证码、分享、导出和敏感查询频率。
- 密钥只在服务端环境和密钥管理中保存。
- 日志脱敏，不记录 token、微信 code、手机号全值、身份证和支付密文。
- 依赖定期更新和漏洞扫描。
- 数据库定时备份、恢复演练和最小权限账号。

## 18. 非功能要求

- 可用性：核心预约和签到在单节点故障后可恢复。
- 性能：首页和课程列表常规请求目标 P95 小于 500ms，不含微信外部接口。
- 一致性：资金、权益、席位强一致；报表和通知允许最终一致。
- 可观测性：结构化日志、trace_id、慢查询、错误率、队列积压和业务指标。
- 可测试性：单元测试、领域状态机测试、API 契约测试、数据库集成测试和小程序 E2E。
- 可发布性：开发、测试、预生产、生产环境隔离；数据库迁移可回滚或前向修复。
- 灾备：数据库、对象存储和配置均有备份；明确 RPO/RTO。

## 20. 对抗式审查清单

在每个功能进入开发前必须回答：

1. 这个功能改变了哪类事实？
2. 谁可以操作，数据范围是什么？
3. 重复提交会发生什么？
4. 两个请求并发会发生什么？
5. 中途失败能否回滚？
6. 状态是否允许当前转换？
7. 是否影响资金、权益或席位？
8. 是否有不可变流水和审计？
9. 是否泄露其他租户或场馆数据？
10. 报表如何下钻到原始事实？
11. 微信回调重复、延迟或乱序如何处理？
12. 删除、停用和历史记录如何共存？

高风险反例：

- 会员同时点击两次预约。
- 候补转正与普通预约同时抢最后一个席位。
- 教练请假时已有预约和已扣权益。
- 卡在预约后被冻结或过期。
- 支付回调到达两次，或先于前端成功页。
- 退款时部分权益已消费。
- 员工被移出场馆但旧 token 仍有效。
- 场馆改时区、营业时间或课程容量。
- 报表任务重复执行。
- 导出链接被转发给无权限用户。

## 22. 最终验收标准

新系统不是以“185 个旧页面全部复刻”为完成标准，而是：

- 旧系统确认存在的业务能力都有明确处置结果，没有静默遗漏。
- MVP 从场馆配置、排课、发卡到会员预约、签到、扣课形成闭环。
- 每一笔资金和权益变化可解释、可核对、可补正。
- 权限与租户隔离经过自动化测试。
- 微信登录、支付和消息均使用正式服务端协议，无后门。
- 前后端均从源码可重复构建、测试和部署。
- uView Plus 只是可替换 UI 基础，不控制业务模型。
- MySQL 8.0 的能力和限制已在报表、约束、索引和事务设计中显式处理。

## 23. 防遗漏的需求追溯机制

“参考旧系统但不复制旧系统”最容易产生两种失败：一是按新设计删除了实际仍在使用的能力，二是为了追求页面相似把旧缺陷重新实现。必须建立双向追溯矩阵。

证据源：

- `generated/page-inventory.csv`：185 个旧页面。
- `generated/api-catalog.csv`：313 个唯一旧端点及其读写属性。
- `generated/api-usages.csv`：502 个已识别调用点。
- `generated/navigation-references.csv`：页面入口、分享和跳转证据。
- `generated/component-references.csv`：通用与业务组件证据。
- `member-audit.md`、`admin-audit.md`：人工确认的字段、流程和风险。

每条旧页面和旧接口必须进入需求追溯表，并且只能选择一种处置状态：

| 状态 | 含义 |
|---|---|
| `MVP_REBUILD` | 首版按新模型重建 |
| `PHASE_2` | 第二阶段实现，数据模型首版预留 |
| `MERGED` | 被合并到新的统一页面或服务，必须指向新需求 ID |
| `REPLACED` | 用不同交互或平台能力替代，必须说明等价结果 |
| `REJECTED` | 经产品、安全或业务评审明确废弃，必须记录理由 |
| `UNKNOWN` | 尚未理解，不允许进入规格冻结 |

矩阵至少包含：

```text
旧端/旧页面
旧能力描述
证据文件和调用点
用户角色
读/写/资金/权益/权限风险
新领域模块
新需求 ID
新页面或 API
处置状态
验收用例
评审人
```

双向检查：

1. 从旧系统到新系统：185 个页面、313 个端点全部有处置状态，`UNKNOWN=0`。
2. 从新系统到业务目标：每个新需求都有角色、事实来源、权限、状态机和验收用例。
3. 从新 API 到数据库：每个写接口明确事务边界、幂等策略、锁策略和审计记录。
4. 从报表到事实：每个指标可以追溯到订单、资金、权益或预约履约记录。
5. 从 UI 到领域：页面只组合应用服务，不自行决定价格、权限、扣课或退款。

规格冻结门禁：

- 旧页面未处置数为 0。
- 旧接口未处置数为 0。
- 两个旧遗失页面也必须记录为 `REJECTED` 或由新需求替代，不能从矩阵中删除。
- 所有资金、权益、席位和权限相关条目完成对抗式评审。
- 产品、前端、后端和测试共同签署矩阵版本。

旧页面数量不是新页面数量。多个旧报表页可以合并为一个带筛选和下钻的新报表；多个旧卡种组件可以统一为一种权益模型；旧的重复接口可以合并为资源接口。但每次合并都必须在矩阵中留下明确映射。
