# 会员卡耗卡与提成结算模型

## 1. 业务口径

本系统把「预约占用权益」和「实际上课耗卡」分开：

- 预约确认：预占卡权益，避免余额、次数或名额被重复使用。
- 预约取消：释放预占，不产生耗卡价值和提成。
- 手工签到与自动签到：调用同一个幂等履约命令，兑现权益并生成耗卡事实。
- 已结算记录撤销：追加冲正或差额记录，不覆盖历史财务记录。

支付方式只有：

- `online`：在线支付，由支付网关确认成功后发卡。
- `balance`：会员现金钱包余额支付。钱包独立于储值会员卡，不能用某张储值卡购买另一张会员卡。

旧的售卡提成继续作为独立口径保留；新的 B 类提成是「耗卡分成」，二者不得在界面或报表中混为一项。

## 2. 角色边界

现有权限角色（RBAC）只决定账号能做什么，不参与财务计算。

业务分成角色单独维护，并允许一个员工拥有多个角色：

- A / `delivery`：实际上课者，例如教练、助教。
- B / `share`：归属分成者，例如会籍顾问、销售、渠道。

A 类收款人来自场次的实际履约人快照；B 类收款人来自会员卡的归属快照。角色、人员或规则之后发生修改，不追溯改变已生成的结算事实。

同一业务角色存在多名收款人时，该角色的分配比例合计必须为 `10000 bps`。角色或归属的变更按场馆业务日生效：新版本生效前仍使用旧版本，不能因为提前配置未来版本而产生归属空档。

课程课时费是“每个已履约场次的总额”，不是按会员人数重复发放，也不是每增加一种 A 类角色就重复一份。一个场次有多名 A 类履约人时，课时费在全部实际履约人之间按稳定权重只分配一次；所有课时费明细之和必须严格等于课程规则中的场次课时费。

## 3. 公式

金额统一用整数分保存，比例统一用基点保存：`10000 bps = 100%`，`10 个点 = 1000 bps = 10%`。财务运算禁止使用浮点数。

### 3.1 储值卡

```text
耗卡基础价值 = 本次实际扣费金额
耗卡提成 = 耗卡基础价值 * 角色比例
```

### 3.2 次卡

```text
耗卡基础价值 = 实付金额 / 总次数 * 本次耗卡次数
耗卡提成 = 耗卡基础价值 * 角色比例
```

实付金额先确定性分配到每个权益单位，余分按稳定顺序分配。一个价值批次全部耗尽时，累计耗卡基础价值必须严格等于该批次实付金额。

### 3.3 期限卡

```text
当日价值池 = 实付金额 / 合同总天数
单次耗卡基础价值 = 当日价值池 / 当天有效耗卡次数
耗卡提成 = 单次耗卡基础价值 * 角色比例
```

期限卡先把实付金额确定性分配到合同自然日，再把当日价值池分配到当天已履约事件。余分按稳定事件顺序分配，当日所有事件之和必须严格等于当日价值池。

提成也使用同样的守恒规则：同一日、同一业务角色和同一提成比例先计算角色日目标金额，再用最大余数法稳定分配到事件和收款人，不能对每笔极小金额分别四舍五入后造成日累计多发或少发。

以 36500 元年卡、365 天、10% 为例：

- 当日一节课：基础价值 100 元，A 类耗卡提成 10 元，单一 B 类归属人耗卡提成 10 元。
- 当日两节课：每节基础价值 50 元，两位 A 类授课人各 5 元；同一 B 类归属人收到两笔各 5 元，合计仍为 10 元。

需求原示例中的 36.5 元和 18.25 元与给定标准公式不一致，系统以标准公式为准。

`validityDays = N` 表示包含激活日在内的 **N 个服务日**，初始结束日为 `激活日 + (N - 1)`；例如 365 天年卡恰好形成 365 个价值切片。不能沿用旧界面中“结束日再加 N 天”的 N+1 口径，否则会同时造成会员可用区间和日价值分母不一致。

## 4. 价值批次

会员卡不能只保存一个可变的「实付金额」。购买、续费、加次、付费延期各自形成不可变价值批次，至少快照：

- 来源订单和支付方式
- 实付金额（分）
- 原始金额权益、次数或合同天数
- 卡产品与规则版本
- 支付时间、来源及估值质量

消费按确定的批次顺序取值。免费赠送形成实付为 0 的独立批次，不摊薄既有付费批次；无法确定实付的历史人工发卡标记为 `derived` 或 `unknown`，不得静默按当前卡价补算历史提成。

人工加次形成独立批次：明确免费赠送时实付为 0，无法确认资金来源时标记为 `unknown`。人工减次按 FIFO 消耗现有批次并记录批次分配，冲正时按原分配恢复；不能只修改卡上的缓存次数，否则后续加次会错误复用已经减掉的旧实付价值。一次耗卡跨越已知与未知批次时，已知部分仍保留可验证价值，未知部分单独标记，不能让未知部分吞掉或复用已知价值。

## 5. 期限卡日桶与调整

期限卡按 `(member_card_id, business_date)` 建立日桶。当天新增、撤销或补录耗卡时：

1. 锁定日桶。
2. 按稳定顺序重算全部有效事件。
3. 比较上一个计算版本。
4. 向结算账本追加差额或冲正行。

普通配置修改不追溯。已关账月份出现迟到签到或冲正时，差额进入后续调整批次，不原地改写已关闭期间。

已关闭期间的汇总和明细必须保持不变。关账后产生的追加行记录来源期间，并归入下一个开放期间；尚无开放期间时进入“待归集调整”，由后续期间接收，界面必须明确区分当期正常发生额和以前期间调整额。

服务日期由场次开始时间按场馆时区计算，不使用实际点击签到的时间，避免跨午夜和补签改变财务归属日。

会员卡请假是服务日黑名单，不是一个新的付费批次：

- 请假开始前必须确认请假区间不存在已确认、候补或仍占用权益的预约；存在时拒绝开始，不能静默取消会员预约。
- 请假区间内禁止新预约、转正和签到履约。
- 结束请假后按实际包含首尾的请假天数顺延期限卡结束日。
- 期限卡价值日序跳过请假日期，原有付费切片顺延到新的末日，实付总额与总服务日数均不被稀释。
- 免费人工延期只扩展可用区间并记录来源；除非有独立、可证明实付的价值批次，否则新增日期保持零价值或 `unknown`，不能复用旧实付金额补提成。

## 6. 幂等与事务

- 预约、取消、签到、钱包调整、购卡、支付回调均使用数据库唯一命令键。
- 手工签到和自动签到共用同一领域命令，每个预约只能有一个原始耗卡事件。
- 余额购卡在同一数据库事务内完成订单、钱包扣款账本、价值批次和发卡；钱包行加锁且余额不得为负。
- 在线支付网络请求在事务外；支付确认后调用与余额支付相同的幂等发卡命令。
- 提成与钱包账本只追加，不物理删除。

## 7. 管理边界

员工端在当前场馆内维护角色、人员归属、卡课扣费规则、课程薪酬规则、钱包调整、耗卡查询和月度关账。

平台超管 Web 使用独立 Admin 会话，所有业务操作显式指定 tenant 和 site，并复用同一领域服务。通用资源 CRUD 不得直接修改耗卡、钱包或提成事实；敏感操作只能通过调整、冲正、重算和关账命令，且进入超管审计日志。

会员端只选择支付方式并查看自己的钱包、订单和耗卡事实，不在前端计算提成或期限卡分摊。

## 8. 历史兼容

- 新表和新字段采用增量迁移，不重写既有权益账本。
- 未来已确认预约可从现有扣费账本映射为预占记录。
- 已完成历史预约只能作为 `legacy_imported` 耗卡事实回填，不能再次扣权益。
- 有已支付订单的会员卡可精确回填价值批次；无可靠实付依据的卡默认不生成历史提成。
- 旧工资快照保留为 `legacy` 结果，新报表以追加式结算明细为数据源。
- 上线前执行 dry-run 对账：卡余额/次数、未完成预约预占、订单实付、钱包余额、耗卡价值和提成总额。

## 9. 验收不变量

- 同一命令重复提交不会重复扣权益、钱包或提成。
- 次卡一个价值批次全部耗尽后的耗卡价值合计等于实付金额。
- 期限卡某业务日所有有效事件的耗卡价值合计等于当日价值池。
- 结算明细按教练、B 类角色、会员、课程和卡项聚合后的净额一致。
- 冲正前后净额正确，历史原始行不被覆盖。
- 规则、角色、人员归属修改不改变历史快照。
- 租户和场馆之间无法读取或写入对方数据。
